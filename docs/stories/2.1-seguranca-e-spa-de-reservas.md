## Story

**Como** usuário autenticado do sistema,
**quero** que a API respeite os perfis e impeça reservas sobrepostas, e usar uma SPA para consultar recursos e reservas,
**para que** as operações sejam autorizadas no servidor e os fluxos principais possam ser usados pela interface.

## Acceptance Criteria

1. `POST /recursos`, `PUT /recursos/{id}` e `DELETE /recursos/{id}` exigem `ADMINISTRADOR`. Os métodos recebem o JWT por `@AuthenticationPrincipal` e rejeitam principal nulo; chamadas anônimas recebem 401, perfis não administradores recebem 403 e administradores mantêm os comportamentos de sucesso existentes.
2. `GET /usuarios` e `GET /usuarios/{id}` exigem autenticação, sem restringir os perfis autenticados. `DELETE /usuarios/{id}` é exclusivo de `ADMINISTRADOR`. A matriz automatizada cobre anônimo, `SOLICITANTE`, `RESPONSAVEL` e `ADMINISTRADOR`.
3. `POST /manutencoes` e `GET /manutencoes` autorizam somente `ADMINISTRADOR` ou `RESPONSAVEL`; anônimos recebem 401 e `SOLICITANTE` recebe 403.
4. `POST /reservas` permite exclusivamente o perfil `SOLICITANTE`. O claim `profile` do JWT é validado no controller, divergências lançam `AccessDeniedException` e a autorização declarativa não aceita `RESPONSAVEL`, `ADMINISTRADOR` nem aliases legados. Anônimo recebe 401; os demais perfis recebem 403.
5. A criação de reserva verifica conflitos do recurso independentemente do status inicial. Reservas sobrepostas do mesmo recurso, inclusive quando ambas seriam `PENDENTE`, resultam em `ConflitoReservaException` e HTTP 409. Reservas adjacentes, cujo fim coincide com o início da próxima, continuam permitidas.
6. A consulta de conflitos da aplicação considera `PENDENTE`, `APROVADA` e `EM_USO`, sem remover a proteção existente para conflitos de agenda do responsável. Os detalhes do conflito continuam identificando recurso e intervalo.
7. Uma migração SQL versionada para PostgreSQL cria `EXCLUDE USING gist` em `tb_reservas`, combinando `recurso_id` com igualdade e o intervalo semiaberto `[data_inicio, data_fim)` com sobreposição, somente para `PENDENTE`, `APROVADA` e `EM_USO`. A migração prepara a operator class necessária (`btree_gist`) e não apaga nem altera reservas existentes para contornar conflitos.
8. Testes PostgreSQL demonstram que o banco rejeita fisicamente períodos sobrepostos para os três status ativos, permite intervalos adjacentes e não aplica a restrição a outros status. A resposta da API para a violação de integridade permanece HTTP 409. Os testes H2 existentes continuam executáveis; não se afirma que H2 oferece a constraint PostgreSQL.
9. A SPA é servida pela própria aplicação Spring Boot, na mesma origem, com um único `src/main/resources/static/index.html`, um único `src/main/resources/static/styles.css` e módulos separados `js/api.js`, `js/auth.js`, `js/app.js`, `js/recursos.js` e `js/reservas.js`. Não são introduzidas dependências de frontend ou páginas HTML/CSS adicionais.
10. Recursos estáticos da SPA podem ser carregados sem JWT, mas os endpoints da API continuam exigindo autenticação e autorização. A configuração mantém os caminhos API protegidos mesmo quando a SPA é servida publicamente, evitando que `permitAll` de estáticos libere rotas de negócio.
11. `api.js` centraliza a URL-base, headers, Bearer Token, leitura de respostas e propagação de erros HTTP. Respostas 401 limpam a sessão inválida e retornam à tela de autenticação; respostas 403 informam falta de permissão; respostas 409 da criação de reserva apresentam feedback de conflito sem falha silenciosa.
12. Como a API é um OAuth2 Resource Server e não possui endpoint de login/emissão de JWT, a tela de autenticação recebe um JWT emitido externamente confiável. `auth.js` mantém o token somente na sessão do navegador (`sessionStorage`), extrai `sub` e `profile` para a interface, oferece encerramento de sessão e não registra nem expõe o token em mensagens. A autorização efetiva permanece sempre no backend.
13. Usuários autenticados podem listar recursos e reservas. A interface de recursos só oferece criação a `ADMINISTRADOR`; a interface de reservas só oferece criação a `SOLICITANTE`. Estados/status das reservas são exibidos e ações não permitidas não são apresentadas como disponíveis. O backend continua sendo a autoridade mesmo se a interface for contornada.
14. A SPA permite entrar/sair, navegar entre login e painel, listar recursos, criar recurso quando autorizado, listar reservas e criar reserva quando autorizado. O teste de fumaça confirma o carregamento de todos os módulos e os fluxos de sucesso, 401, 403 e 409 em navegador.
15. O README documenta como iniciar/abrir a SPA, a origem do JWT esperado, as roles suportadas e a migração PostgreSQL, sem incluir token ou segredo de produção.

### Baseline técnico observado

- Backend: Java 21, Spring Boot 3.2.4, Spring MVC, Spring Data JPA, JWT HS256 e H2 por padrão; PostgreSQL/Testcontainers já são usados nos testes de concorrência. [Source: `pom.xml`; `src/main/resources/application.properties`; `src/test/java/br/edu/organizacaorecursos/ReservaConcorrenciaPostgresIntegrationTest.java`]
- Não existe endpoint de login ou emissão de token: a API valida Bearer JWT recebido do cliente. Não inventar rota ou provedor de autenticação; o fluxo da SPA recebe um token existente. [Source: `README.md`#Autenticação da API; `src/main/java/br/edu/organizacaorecursos/config/SecurityConfig.java`]
- `SecurityConfig` protege por padrão as rotas que não estão explicitamente liberadas; os arquivos estáticos devem ser liberados com paths específicos, mantendo os endpoints API autenticados.
- Os controllers estão em `src/main/java/br/edu/organizacaorecursos/controller/`; a regra de reserva está em `service/ReservaService.java`; a query de conflitos está em `repository/ReservaRepository.java`; o enum gravado usa `StatusReserva`.
- `Reserva` usa `tb_reservas`, `recurso_id`, `data_inicio`, `data_fim` e enum persistido como string. `LocalDateTime` corresponde ao intervalo PostgreSQL sem fuso (`tsrange`), usando limites `[)` para permitir reservas adjacentes. [Source: `src/main/java/br/edu/organizacaorecursos/domain/Reserva.java`]
- O projeto atualmente não contém migrações em `src/main/resources/db/migration/` nem configuração de Flyway. A constraint pedida é específica de PostgreSQL e precisa ser versionada/aplicada/testada nesse banco; não simular sua garantia em H2. A aplicação da migração a bancos existentes não deve ser silenciosa.
- A SPA é servida pela mesma origem em `src/main/resources/static/`, evitando configuração CORS para a integração local com os endpoints.

### Decisões de sessão e segurança do navegador

- O armazenamento é `sessionStorage`, não `localStorage`, para limitar a persistência ao contexto da sessão do navegador. Isso não torna o token imune a XSS; não incluir scripts de terceiros, evitar `innerHTML` com dados de API e manter autorização no servidor.
- O JWT contém `sub` e `profile`; a decodificação no navegador serve somente para adaptar a interface. O backend valida assinatura/expiração e decide cada acesso.
- Exibir recursos e reservas para usuários autenticados; mostrar criação de recurso apenas a `ADMINISTRADOR` e criação de reserva apenas a `SOLICITANTE`. As ações são sempre validadas novamente pelo backend.
